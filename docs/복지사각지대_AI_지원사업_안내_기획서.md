# 복지 사각지대 해소를 위한 AI 공공지원사업 안내 서비스 기획서

_작성일: 2026-09-04 · 문서 버전: v0.1 (데모 단계)_

---

## 1. 문제 정의

### 1.1 한 문장 정의

> 소득 취약 노인은 자신이 받을 수 있는 공공지원사업이 있다는 사실, 자신이 그 대상이라는 사실, 그리고 신청에 무엇이 필요한지를 스스로 알 수 없고, 이를 대신 알아봐 줄 사람(가족·요양보호사·복지사)은 존재하지만 시간과 제도 지식의 한계로 상당수가 누락된다. 기존 서비스(보조금24, 토스 숨은지원금 등)는 "본인이 직접 검색하고 로그인하는 사람"을 전제로 하기 때문에 이 집단에는 닿지 않는다.

### 1.2 문제의 네 단계

당사자가 지원을 받기까지 넘어야 하는 문턱은 네 개이며, 각 단계마다 이탈이 발생한다.

| 단계 | 문턱 | 왜 막히는가 |
|---|---|---|
| ① 인지 | 지원사업이 있다는 것을 모름 | 본인이 대상인 줄 모르니 검색 자체를 안 함 |
| ② 해당 여부 판단 | 자기 상황에 대입 못 함 | "중위소득 60% 이하", "부양의무자 기준" 같은 조건을 자기 말로 못 옮김 |
| ③ 이해 | 공고문을 읽어도 모름 | 법령·행정 문체, 예외 조항, 서류 명칭 |
| ④ 신청 | 절차에서 포기 | 신분증·주소·자녀 소득 등 자기 정보를 모름, 방문 준비 미비, 재방문 |

핵심 통찰: **정보는 이미 존재한다.** 부족한 것은 "정보"가 아니라 "정보를 개인 상황에 대입하고 절차 언어로 번역하는 노동"이다. 이 번역 노동이 AI가 들어갈 정확한 자리다.

### 1.3 사각지대에 대한 정의

기존 서비스가 놓치는 이유 중 하나는 "공식 조건"과 "실제 상황"의 불일치다. 대표적으로:

- 자녀가 있지만 연락이 끊겨 부양을 받지 못함 (서류상 부양의무자 존재)
- 명의상 재산은 있으나 처분·활용 불가 (거주 중인 노후 주택, 분쟁 중인 토지)
- 소득이 있으나 불규칙·비공식 (폐지 수집, 일용직)
- 주민등록상 주소와 실제 거주지가 다름
- 배우자 사망 후 명의·계좌가 정리되지 않음
- 본인이 장애·질병 사실을 "장애"로 인식하지 않아 진술하지 않음

서비스는 이런 상황을 **질문 설계 단계에서** 잡아내야 한다. 조건표를 그대로 묻는 것이 아니라 상황을 묻고, 그 상황을 조건으로 변환하는 것이 AI의 역할이다.

### 1.4 실제 사용자는 누구인가

가장 취약한 당사자가 앱을 직접 완주할 가능성은 낮다. 따라서 서비스는 **두 종류의 사용자를 처음부터 전제**한다.

| 사용자 | 역할 | 서비스가 해결하는 것 |
|---|---|---|
| 본인 (노인) | 상황을 말한다 | 큰 글씨, 한 화면 한 질문, 모르면 넘김 |
| 보호자 (자녀·요양보호사·복지사·이웃) | 본인이 모르는 정보를 채우고 신청을 돕는다 | 1인당 감당 가능한 케이스 수 확대, 제도 지식 보완 |

보호자는 이미 존재하며, 이미 이 노동을 하고 있고, 소진되고 있다. 서비스의 성공 지표는 "노인이 혼자 완주했는가"가 아니라 "본인+보호자 조합이 주민센터에 한 번 방문해서 신청을 끝냈는가"이다.

## 2. 서비스 목표와 범위

### 2.1 목표

"몰라서 못 받는" 사람을 "알고, 준비된 상태로 주민센터에 가는" 사람으로 바꾼다.

### 2.2 성공 기준 (데모 단계)

- 사용자가 자기 상황 입력을 끝까지 완료하는 비율 (본인 단독 / 보호자 개입 구분)
- 추천된 사업 중 실제로 신청 자격이 맞는 비율 (복지사 검수 기준)
- "설명을 읽고 이해했다"고 답하는 비율 (쉬운 언어 검증)
- 주민센터 방문 시 준비물 누락으로 재방문한 사례 수 (감소 목표)

### 2.3 범위

| 포함 | 제외 (이번 데모) |
|---|---|
| 노인(65세+) 대상 소득 기반 복지·지원사업 | 청년·장애·아동 등 타 대상군 |
| 중앙부처 + 지자체 사업 | 민간 복지 서비스 |
| 상황 입력 → 사업 매칭 → 쉬운 설명 → 주민센터 전달 메시지 | 실제 온라인 신청 대행, 본인인증 연동 |
| 웹 기반 모바일 앱 화면 데모 | 네이티브 앱 배포 |

## 3. 사용자 여정과 기능

### 3.1 전체 흐름

```
[진입] 본인 / 보호자 선택
   ↓
[1단계] 상황 입력 (대화형 질문)
   ├─ 본인이 모르는 질문 → "보호자에게 물어보기"로 넘김
   └─ 보호자 화면에서 보완 입력
   ↓
[2단계] 지원사업 매칭 (API 조회 + LLM 필터링)
   ↓
[3단계] 쉬운 말 설명 + 준비물 안내
   ↓
[4단계] 주민센터 전달 메시지 생성
   ├─ 화면 제시용 (방문 시 보여주기)
   ├─ 보호자에게 전송
   └─ (조건부) 주민센터 담당자에게 전송
```

### 3.2 진입: 본인 / 보호자 선택

첫 화면은 두 개의 큰 버튼만 둔다.

- **"제가 직접 알아볼게요"** → 본인 모드 (큰 글씨 기본 적용, 음성 안내 옵션)
- **"어르신을 도와드리려고 해요"** → 보호자 모드 (자녀 / 요양보호사·활동지원사 / 복지사·공무원 / 이웃·지인 중 선택)

보호자 모드에서는 "어르신 본인 상황을 대신 입력"하는 것이며, 보호자 자신의 정보는 부양 관계 판단에 필요한 최소한만 묻는다.

### 3.3 1단계: 상황 입력 (질문 설계)

이 단계가 서비스의 품질을 결정한다. 원칙은 다음과 같다.

**설계 원칙**

1. 조건을 묻지 않고 상황을 묻는다. ("중위소득 몇 %인가요?" ✗ / "한 달에 손에 들어오는 돈이 대략 얼마인가요?" ○)
2. 한 화면에 한 질문. 선택지는 최대 4개, 글자 크기 최소 20pt.
3. 모든 질문에 **"잘 모르겠어요"** 버튼이 있다. 누르면 그 질문은 보호자 보완 목록으로 이동하고 다음 질문으로 넘어간다.
4. 정부 사업이 실제로 요구하는 정보를 역산해서 질문을 구성한다. (선정기준·부양의무자·재산·거주 요건)
5. 사업이 요구하지 않더라도 실질적으로 필요한 정보(거동 가능 여부, 계좌 보유 여부, 신분증 보유 여부)를 묻는다. 신청 단계 이탈을 막기 위해서다.

**질문 영역과 예시**

| 영역 | 본인에게 묻는 방식 | 사각지대 포착 질문 | 보호자 보완 항목 |
|---|---|---|---|
| 기본 | 나이, 사는 곳(시·군·구까지) | "지금 사시는 곳과 주민등록 주소가 같으세요?" | 정확한 주소, 주민등록 여부 |
| 가구 | 혼자 사시는지, 같이 사는 분 | — | 세대 구성 |
| 자녀·부양 | "자녀가 있으세요?" → 있으면 "연락은 되세요?", "생활비를 받으세요?" | 연락 두절, 관계 단절, 자녀의 경제 형편 | 자녀 소득·재산 대략, 부양 여부 |
| 소득 | "한 달에 들어오는 돈이 대략 얼마인가요?" (구간 선택) + 어디서 들어오는지 (연금 / 일 / 자녀 / 없음) | 불규칙 소득, 비공식 노동 | 국민연금·기초연금 수령액, 근로소득 |
| 재산 | "지금 사시는 집이 본인 소유인가요? 전세? 월세?" | 명의만 있는 재산, 처분 불가 재산 | 공시가격, 전세보증금, 예금 대략 |
| 건강·돌봄 | "혼자 장 보러 다니실 수 있나요?", "병원에 정기적으로 다니세요?" | 장애 미등록, 치매 초기 | 진단명, 장기요양등급 여부 |
| 신청 준비 | "신분증 갖고 계세요?", "본인 이름 통장 있으세요?" | 계좌 없음, 신분증 분실 | 계좌번호, 재발급 필요 여부 |
| 이미 받는 것 | "지금 나라에서 받는 돈이 있으세요?" (기초연금 / 생계급여 / 모름) | 수급 여부 불확실 | 현재 수급 내역 |

**LLM의 역할 (1단계)**

- 사용자의 자유 답변("아들이 있긴 한데 몇 년째 연락이 안 돼요")을 구조화된 조건(부양의무자 존재, 실질 부양 없음 → 부양의무자 기준 완화 검토 대상)으로 변환
- 답변 간 모순 감지 후 되묻기 ("혼자 산다고 하셨는데, 아까 손주랑 같이 계신다고 하셨어요. 손주가 같이 사나요?")
- 답변에 따라 다음 질문을 동적으로 결정 (자녀 없음 → 자녀 관련 질문 전체 생략)

**보호자 연결 방식**

- 본인이 "잘 모르겠어요"를 누른 항목은 하나의 보완 목록으로 묶인다.
- 본인 화면에 **"이 질문들은 자녀분이나 도와주시는 분께 물어보면 돼요"** 안내와 함께 링크·QR 코드 생성.
- 보호자가 링크로 접속하면 해당 항목만 입력하는 짧은 화면이 뜬다. (로그인 없음, 세션 코드 기반)
- 보완이 완료되면 본인 화면에서 다음 단계로 진행 가능. 보완 없이도 "지금 아는 것만으로 알아보기"가 가능해야 한다. (불완전 정보로도 후보군은 제시)

### 3.4 2단계: 지원사업 매칭

**데이터 소스**

| 소스 | 내용 | 활용 |
|---|---|---|
| 행정안전부 「대한민국 공공서비스(혜택) 정보」 API (보조금24 원천) | 중앙부처·지자체·교육청 등 약 7,500개 서비스 | 1차 후보군 확보 |
| 한국사회보장정보원 「중앙부처복지서비스」 / 「지자체복지서비스」 API (복지로) | 지원대상·선정기준·신청방법 필드 포함 | 조건 매칭의 주 소스 |
| 지자체 홈페이지 공고 (크롤러, 선택) | API 미반영 소규모 사업 | 데모 후반 검토 |

**매칭 파이프라인**

1. 거주지(시·군·구) + 연령 + 대상군(노인)으로 API 1차 필터 → 수십~수백 건
2. LLM에게 각 사업의 "지원대상·선정기준" 원문과 사용자 상황 요약을 함께 전달 → 해당 / 해당 가능(조건 확인 필요) / 비해당 3분류 + 판단 근거
3. "해당 가능" 항목은 어떤 정보가 더 있으면 확정되는지 명시 → 보호자 보완 목록에 자동 추가
4. 우선순위 정렬: 금액 크기, 신청 기한, 자격 확실성

**품질 통제**

- LLM 판단 결과에 항상 원문 근거(선정기준 문장)를 첨부. 사용자에게는 숨기되 복지사·보호자 모드에서는 열람 가능.
- "확실히 받을 수 있다"는 표현 금지. "신청해볼 수 있어요 / 주민센터에서 확인이 필요해요"로 통일.
- 데모 단계에서는 복지사 1~2명이 매칭 결과를 샘플 검수하여 정확도 측정.

### 3.5 3단계: 쉬운 말 설명

각 사업을 다음 형식으로 변환한다.

- **한 줄**: 이게 뭔지 ("매달 생활비를 보태주는 지원이에요")
- **얼마나**: 금액 또는 혜택 ("한 달에 약 OO만 원")
- **왜 나한테 해당**: 사용자 답변 기준으로 ("혼자 사시고, 한 달 수입이 OO만 원 이하라고 하셔서요")
- **어디로**: 신청 장소 ("사시는 동 주민센터")
- **뭘 가져가야**: 준비물 체크리스트 (신분증, 통장 사본, 필요 시 자녀 관련 서류)
- **주의**: 확인이 필요한 조건 ("자녀분 소득에 따라 달라질 수 있어요")

**언어 기준**

- 초등 4~5학년 수준 어휘, 한 문장 20자 내외
- 행정 용어는 괄호 안에 원어 병기 ("생활비 지원(생계급여)")
- 음성 읽기(TTS) 버튼 제공

### 3.6 4단계: 주민센터 전달 메시지

**목적**: 방문 시 "말로 설명 못 해서" 또는 "정보를 몰라서" 생기는 재방문을 없앤다.

**메시지 구성**

```
[○○ 서비스에서 작성된 신청 안내문입니다]

안녕하세요. 저는 홍길동(1945년생, 81세)입니다.
서울시 ○○구 ○○동에 혼자 살고 있습니다.

다음 지원사업을 신청하고 싶습니다.
  1. 기초생활보장 생계급여
  2. 서울형 긴급복지

제 상황은 다음과 같습니다.
  - 아들 1명이 있으나 5년 이상 연락이 끊겼습니다.
  - 월 수입은 기초연금 약 34만 원뿐입니다.
  - 월세로 거주 중이며 보증금 500만 원입니다.

준비해 온 것: 신분증, ○○은행 통장
확인이 필요한 것: 자녀 소득 관련 서류 (연락 불가하여 준비 못 함)

지원금 입금 계좌: ○○은행 (계좌번호는 방문 시 직접 제시)

이 안내문은 어르신 본인 또는 보호자가 입력한 내용을 바탕으로 자동 작성되었으며,
정확한 자격 판단은 담당자 확인이 필요합니다.
```

**전달 방식 (3단계로 설계)**

| 방식 | 설명 | 데모 포함 |
|---|---|---|
| 화면 제시 | 방문 시 휴대폰 화면 또는 출력물로 담당자에게 보여줌 | ○ (기본) |
| 보호자 전송 | 보호자 휴대폰으로 문자·카카오톡 공유, 동행 시 활용 | ○ |
| 주민센터 직접 전송 | 담당 부서 이메일·팩스로 사전 발송 | △ (조건부, 아래 참고) |

**직접 전송에 대한 설계 판단**

주민센터가 개인 서비스에서 발송한 메시지를 공식 접수하지는 않는다. 따라서 "자동 발송"은 (a) 사용자의 명시적 동의 후 (b) 참고자료로 사전 공유되는 것이며, 접수를 대체하지 않는다는 점을 화면에 명시한다. 데모에서는 발송 화면과 미리보기까지 구현하고 실제 발송은 이메일 초안 생성으로 갈음한다. 협력 지자체가 생기면 담당자 지정 채널로 확장한다.

**계좌번호 처리**

계좌번호는 메시지 본문에 포함하지 않고 "방문 시 직접 제시"로 처리한다. 은행명만 표기. 취약계층 대상 금융 정보가 제3자 채널을 거치는 위험이 편익보다 크다.

## 4. 접근성 설계

| 항목 | 기준 |
|---|---|
| 글자 크기 | 기본 18pt, 큰글자 모드 24pt+ (전역 토글, 첫 화면에서 즉시 전환 가능) |

| 입력 | 타이핑 최소화. 선택지 버튼 우선, 숫자는 구간 선택, 자유 입력은 음성 입력 옵션 |

| 이탈 방지 | 중간 저장, 세션 코드로 재접속 (로그인 없음) |
| 언어 | 존댓말, 짧은 문장, 부정문 지양 |

## 5. 기술 구성 (데모)

### 5.1 아키텍처

```
[웹 프론트엔드: 모바일 앱 형태의 반응형 웹]
   ├─ 본인 모드 / 보호자 모드
   ├─ 큰글자 토글, TTS
   └─ 세션 코드 기반 상태 공유
          ↓
[백엔드 API]
   ├─ 질문 흐름 엔진 (동적 분기)
   ├─ 공공데이터 API 어댑터 (보조금24 / 복지로)
   ├─ LLM 오케스트레이션
   │    ├─ 답변 구조화 (자유 텍스트 → 조건)
   │    ├─ 사업 매칭·분류
   │    ├─ 쉬운 말 변환
   │    └─ 전달 메시지 생성
   └─ 세션 저장소 (개인정보 최소 보관, 만료 정책)
```

### 5.2 LLM 활용 원칙

- 상용 LLM API 사용. 프롬프트에 사업 원문을 그대로 넣어 근거 기반으로 판단하도록 하고, 출력은 구조화(JSON)로 받는다.
- 환각 방지: 사업명·금액·기관명은 LLM이 생성하지 않고 API 데이터에서 그대로 가져온다. LLM은 판단과 문장 변환만 담당.
- 모든 LLM 출력에 "확인 필요" 플래그를 둘 수 있게 하고, 확신도가 낮으면 사용자에게 그대로 보여준다.

### 5.3 데이터·개인정보

- 로그인·본인인증 없음. 이름·연령·거주지·상황은 세션 단위로 보관, 일정 기간 후 자동 삭제.
- 주민등록번호·계좌번호는 수집하지 않는다.
- 보호자 링크는 세션 코드 기반이며 만료 시간을 둔다.
- 개인정보 처리방침 화면을 큰 글씨로 제공하고, 입력 전에 "이 정보는 지원사업을 찾는 데만 쓰이고 저장되지 않아요"를 명시.

## 6. 데모 범위와 일정

### 6.1 데모에서 반드시 보여줄 것

1. 본인/보호자 선택 → 큰글자 전환
2. 상황 입력 10~12개 질문, "잘 모르겠어요" → 보호자 보완 링크 생성
3. 보호자 화면에서 보완 입력 → 본인 화면 반영
4. 실제 API 데이터 기반 사업 매칭 결과 3~5건, 각각 쉬운 말 설명 + 준비물
5. 주민센터 전달 메시지 미리보기 + 보호자 공유

### 6.2 단계

| 단계 | 내용 | 기간(안) |
|---|---|---|
| 0 | 복지사·주민센터 담당자 2~3명 인터뷰: 실제 재방문 사유, 자주 빠지는 서류, 사각지대 사례 수집 | 1주 |
| 1 | 질문 설계 확정, 데이터 API 활용신청·스키마 분석 | 1주 |
| 2 | 프론트 화면 + 질문 엔진 + 보호자 연결 | 2주 |
| 3 | 매칭 파이프라인 + 쉬운 말 변환 + 메시지 생성 | 2주 |
| 4 | 노인·보호자 5~10명 사용성 테스트, 복지사 검수 | 1주 |

### 6.3 0단계가 중요한 이유

이 기획서의 질문 목록과 사각지대 유형은 가설이다. 실제 담당자가 "이 서류 때문에 다시 오시는 분이 제일 많다"고 말하는 항목이 질문 설계의 최우선이어야 한다. 인터뷰 없이 만들면 정확한 문제를 예쁘게 푸는 서비스가 된다.

## 7. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| LLM이 자격 있다고 잘못 판단 → 헛걸음 | "확실" 표현 금지, 근거 첨부, 복지사 검수, 담당자 확인 문구 상시 노출 |
| 노인이 입력 중 이탈 | 세션 저장, 보호자 보완, 불완전 정보로도 후보 제시 |
| API 데이터의 선정기준이 비정형·누락 | 데모 대상 사업을 노인 대상으로 좁혀 수작업 보정, 크롤러 보조 |
| 주민센터가 메시지 수신을 거부·무시 | 기본은 화면 제시, 직접 전송은 협력 지자체 확보 후 |
| 개인정보 유출 | 최소 수집, 무로그인, 자동 삭제, 계좌번호 미수집 |
| 사각지대 상황을 조건으로 잘못 변환 | 변환 결과를 사용자에게 다시 확인 ("자녀분과 연락이 안 되는 상황으로 이해했어요, 맞나요?") |
